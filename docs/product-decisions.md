# Продуктовые решения MVP

## Зафиксировано

- Канал: Telegram.
- Языки: русский и английский. Язык общения и язык документа — разные настройки.
- Интервью: только диалоговое; импорт готового CV/LinkedIn отложен.
- Выход: Human PDF и ATS PDF.
- Шаблоны: по одному шаблону каждого вида в первом релизе; PDF Designer Agent готовит шаблоны и layout-specification.
- Заполнение профилем выполняет отдельный детерминированный renderer.
- Файлы выдаются в Telegram; отдельная web-ссылка в MVP не нужна.
- PostgreSQL; базовый retention для карьерных данных — 7 дней.
- LLM: AnyModel; стартовая модель — DeepSeek v4 Flash, если она доступна через требуемый API-контракт.
- Сценарии первого релиза: backend developer и frontend developer; при отсутствии подходящего сценария используется generic fallback.
- Пользователь выбирает универсальное резюме или вариант под вакансию.
- Базовые диалоги, согласия, баланс, выбор сценария, статусы и платежи обслуживаются детерминированным bot script без LLM.
- Interview Agent и последующие LLM-операции запускаются только после атомарного списания баланса за конкретную операцию.
- Preview — отдельная платная операция; начальный баланс должен покрывать одну preview-генерацию.
- ATS preview до оплаты не выдаётся.
- Способы оплаты в MVP: Telegram Stars и СБП. Пользователь выбирает доступный способ перед оплатой.
- Пользовательские правки проходят через Interview Agent и моральные/безопасностные фильтры; неподходящие запросы отклоняются кратко, без выполнения.

## LLM и AnyModel

Название модели нельзя считать достаточным выбором. До интеграции AnyModel нужно проверить:

1. structured output/JSON Schema или function calling;
2. качество русского и английского языка;
3. длину контекста, цены, лимиты и rate limits;
4. политику хранения и использования данных провайдером;
5. timeout, retry и доступность fallback-модели.

AnyModel предоставляет OpenAI-compatible gateway:

- base URL: `https://anymodel.org/v1`;
- chat endpoint: `POST /v1/chat/completions`;
- авторизация: `Authorization: Bearer $ANYMODEL_API_KEY`;
- каталог моделей: `GET /v1/models`;
- информация о модели: `GET /v1/models/info?id=...`;
- баланс ключа провайдера: `GET /v1/balance`.

ID модели нужно брать точно из каталога, включая provider prefix (`am/...`, `cc/...`, `xai/...` и т. п.). Короткое имя может выбрать другой route и иметь другой коэффициент стоимости.

Документация явно описывает для Chat Completions параметры `model`, `messages`, `stream`, `temperature`, `max_tokens` и `reasoning_effort`. `response_format`/JSON Schema и client-side function calling в разделе Chat Completions не подтверждены. Поэтому до capability-теста нельзя считать structured output гарантированным.

Внутри проекта нужен provider adapter, не зависящий от формата AnyModel:

```text
generate(request, model, schema?) -> response(text, structured_data?, usage, provider_request_id)
```

Адаптер обязан иметь timeout, ограниченный retry, обработку rate limit и безопасное удаление PII из технических логов. В доменный код нельзя протекать формат конкретного провайдера.

Точный ID и наличие DeepSeek v4 Flash нужно получить через `GET /v1/models`; название из пользовательского описания само по себе не является достаточным конфигурационным значением. Если нужной модели нет, выбирается следующая самая дешёвая модель, которая проходит capability-тесты. Модель для финальной нормализации может быть надёжнее дешёвой модели обычного диалога.

Пока structured output не подтверждён, Normalizer Agent должен:

1. просить только JSON без markdown и дополнительных комментариев;
2. ограничивать `temperature` и задавать достаточный `max_tokens`;
3. извлекать JSON безопасным parser-ом;
4. валидировать Pydantic/JSON Schema;
5. выполнять максимум один ограниченный repair/retry;
6. при неуспехе переводить job в контролируемый `failed`, не генерируя PDF.

Важно: баланс AnyModel — баланс ключа провайдера в balance tokens, а баланс пользователя ResumeMaker — отдельный внутренний ledger. Их нельзя смешивать.

Стоимость chat-вызова AnyModel считается так:

```text
ceil(prompt_tokens * coefficient.input + completion_tokens * coefficient.output)
```

Коэффициенты берутся из `GET /v1/models`. Перед LLM-job приложение должно оценить верхнюю стоимость, зарезервировать пользовательские кредиты, а после ответа списать фактическую стоимость по `usage` и вернуть разницу. При ошибке до результата кредит возвращается по idempotent recovery-пути.

### Ошибки AnyModel

Адаптер должен сохранять `provider_request_id` и безопасно классифицировать ошибки:

- `400` — ошибка запроса; обычно retry бесполезен. Особый код `output_budget_exhausted` означает, что токены уже были потрачены и списаны, поэтому повтор требует отдельной budget/retry policy.
- `401` — неверный или отозванный API key; не повторять автоматически.
- `402` — закончился баланс ключа AnyModel; это не пользовательская ошибка ResumeMaker и не должно маскироваться под недостаток пользовательских кредитов.
- `403` — аккаунт провайдера неактивен/заблокирован; не интерпретировать как необходимость пополнить баланс.
- `404`/`406` — model или endpoint не поддерживается; выбрать конфигурационный fallback только после проверки.
- `429` — rate limit; использовать `Retry-After` и ограниченный backoff.
- `500`/`503` — временная ошибка сервиса; ограниченный retry с jitter. `503` может означать `bad_gateway`, `gateway_timeout` или `service_unavailable`.

Ошибки и логи не должны содержать prompt или PII. Внутри job сохраняются код, безопасное сообщение, provider request ID и номер попытки.

## Сценарии вакансий

Сценарий хранится как версионируемая конфигурация, а не только как prompt:

```text
scenario_id, scenario_version, target_role, required_sections,
optional_sections, question_plan, completion_rules
```

Агент меняет формулировки и глубину уточнений, но не обязательные поля. `completion_rules` проверяются кодом. Если сценарий не найден, используется generic scenario.

## Баланс и операции

Баланс — это ledger транзакций, а не единственное изменяемое поле пользователя:

```text
credit_id, user_id, operation_id, amount, type, status, created_at, expires_at
```

Минимальные типы: `initial_grant`, `purchase`, `debit`, `refund`, `expired`.

- Для каждого `operation_id` действует уникальное ограничение на списание.
- Списание и создание job выполняются в одной транзакции или через надёжный transactional outbox.
- При техническом отказе до результата кредит возвращается либо операция переходит в однозначный recovery-status.
- Базовые сообщения не списывают баланс и не отправляют пользовательский текст во внешний LLM.
- Стоимость задаётся по операциям: preview, финальная генерация, повторная нормализация после правки.

## Preview и оплата

Полный PDF с watermark — слабая защита: watermark можно обрезать или удалить. Для MVP:

- preview отправляется в Telegram с заметным watermark;
- ATS preview до оплаты не отправляется;
- после успешной оплаты Human PDF и ATS PDF генерируются заново без watermark;
- платёжные webhook обрабатываются idempotently;
- payment status не смешивается с профилем кандидата.

Нужно отдельно определить, оплачивается ли финальная генерация дополнительным списанием или входит в покупку/стартовый пакет. Это должно быть выражено в таблице тарифов.

Для оплаты в MVP поддерживаются два независимых маршрута:

1. **Telegram Stars** — нативная оплата внутри Telegram.
2. **СБП** — переход пользователя на защищённую страницу выбранного российского банка/эквайера с оплатой по QR-коду или deep link СБП. Бот не принимает и не хранит банковские реквизиты.

СБП — это платёжная схема, а не конкретный провайдер. До реализации нужно выбрать банк/эквайера, который предоставляет API создания платежа, ссылку/QR, server-to-server webhook, проверку статуса и возвраты. Выбор зависит от страны и юридического статуса оператора, валюты и требований к онлайн-кассе/чекам.

Для обоих маршрутов обязательны:

- единый внутренний `payment_id` и `operation_id`;
- `payment_method: telegram_stars | sbp`;
- отдельная запись внешнего `provider_payment_id`;
- идемпотентный create-payment и webhook по ключу провайдера;
- проверка подписи webhook и сверка суммы, валюты, товара, пользователя и статуса на сервере;
- подтверждение успешной оплаты только после server-to-server проверки, а не по нажатию кнопки или возврату пользователя в Telegram;
- безопасная повторная отправка ссылки/QR при незавершённом платеже;
- expiration для платёжной сессии и однозначная обработка `pending`, `paid`, `failed`, `expired`, `refunded`;
- возврат средств с сохранением audit trail и без повторного начисления кредитов.

Для СБП пользовательский поток выглядит так:

```text
Telegram -> выбор СБП -> создание payment session -> одноразовая ссылка/QR
-> приложение банка пользователя -> webhook эквайера -> сверка платежа
-> начисление внутреннего ledger -> запуск оплаченной операции
```

Возврат пользователя из браузера в Telegram является только UX-событием и не подтверждает оплату. Если webhook задержан, бот показывает `payment_pending` и предлагает проверить статус, не создавая второе списание или второе начисление.

До выбора конкретного эквайера остаются открытыми: страна регистрации оператора, валюта, договор с банком, налоговый/кассовый контур, комиссия, лимиты СБП, срок жизни QR и правила возвратов. Telegram Stars и СБП не должны смешиваться в одной внешней транзакции, но оба пополняют один и тот же внутренний ledger после подтверждённой оплаты.

## Хранение и Telegram-файлы

Рекомендуемое разделение retention:

- raw transcript, extracted facts и normalized JSON — 7 дней;
- preview — удалить после финала или по короткому TTL;
- финальный PDF — 7 дней либо раньше по запросу удаления;
- payment audit — по требованиям платёжной системы и законодательства, даже если карьерные данные удалены раньше;
- технические логи — минимальный срок и без полного PII.

Telegram может хранить отправленный файл в чате, но не является контролируемым архивом приложения: пользователь может удалить сообщение, а правила и лимиты Telegram могут измениться. В базе хранятся metadata/hash/status и, при необходимости, `telegram_file_id`; локальные бинарные копии удаляются по retention policy.

## Юрисдикция и согласие

Юрисдикцию нельзя определить только по языку пользователя. Она зависит от страны регистрации оператора, целевых рынков, платёжного провайдера и стран передачи данных. До определения этих сведений нельзя утверждать, что конкретный текст юридически достаточен.

До публичного запуска нужно определить юридическое лицо/оператора, целевые страны и получить консультацию специалиста по персональным данным в юрисдикции оператора. Для международного baseline следует предусмотреть прозрачное уведомление, минимизацию данных, удаление и экспорт, а также отдельное согласие на передачу текста внешнему AI-провайдеру.

Пример продуктового текста, не являющийся готовой юридической офертой:

> Я согласен(на) на обработку и хранение предоставленных мной данных для подготовки резюме в течение срока, указанного в политике сервиса. Я понимаю, что текст интервью может передаваться внешнему AI-провайдеру для обработки. Я могу отказаться от продолжения и запросить удаление данных в соответствии с политикой сервиса.

В интерфейсе решения должны быть раздельными: согласие на обработку/хранение и согласие на передачу внешнему AI-провайдеру. Для каждого события сохраняются версия текста, timestamp, user/consent ID, результат и источник интерфейса.
