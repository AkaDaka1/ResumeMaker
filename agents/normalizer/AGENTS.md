# Правила Normalizer Agent

## Роль

Normalizer Agent преобразует подтверждённые turns/facts в типизированный candidate profile для рендеринга. Это слой извлечения и проверки, а не копирайтер и не дизайнер.

## Обязательно

- Принимать только явно заданный входной контракт.
- Принимать `scenario_id`/`scenario_version` и `resume_language` как входные параметры, а не угадывать их из текста.
- Запускаться только из авторизованной job после списания баланса; проверка баланса не является задачей нормализатора.
- Возвращать JSON, валидный относительно конкретной `schema_version`.
- Для каждого существенного поля сохранять evidence/source и статус (`confirmed`, `candidate_stated`, `inferred`, `missing`, `conflict` или эквивалентную согласованную модель).
- Сохранять исходные формулировки достижений там, где их смысл может измениться при перефразировании.
- Выявлять конфликтующие даты, должности, дубликаты и неподтверждённые числа.
- Заполнять `quality.missing_required` и `quality.warnings`, а не скрывать проблемы.
- Выполнять строгую валидацию после ответа модели; при ошибке использовать ограниченный repair/retry или возвращать контролируемую ошибку.
- Записывать model version, prompt version, schema version и input fingerprint.
- Отделять факты кандидата от служебных полей оплаты, preview и watermark; платёжный статус не является содержанием резюме.
- Не считать AnyModel structured output гарантированным: документация Chat Completions явно подтверждает `model`, `messages`, `stream`, `temperature`, `max_tokens` и `reasoning_effort`, но не подтверждает `response_format`/JSON Schema или client-side function calling.
- Принимать ответ только после безопасного JSON parsing и строгой Pydantic/JSON Schema validation; допускается максимум один ограниченный repair/retry.
- При отсутствии валидного JSON переводить job в `failed` и не передавать данные renderer.
- Фиксировать `usage`, provider model ID с prefix и коэффициенты стоимости; не смешивать их с пользовательским балансом.
- Для `output_budget_exhausted` учитывать, что использованные токены уже могли быть списаны; не запускать бесконечный repair/retry.
- При `401`, `403`, `404`, `406` не делать автоматические повторы; при `429` уважать `Retry-After`; при `500`/`503` использовать ограниченный backoff.
- Сохранять безопасные `provider_request_id`/`X-Request-Id` для диагностики без prompt и PII.

## Запрещено

- Галлюцинировать достижения, технологии, даты, уровень языка или названия работодателей.
- Повышать confidence только ради заполнения шаблона.
- Удалять данные из исходного transcript.
- Менять смысл ответа кандидата ради более «продающего» профиля.
- Вызывать PDF-рендерер из prompt/tool без orchestration-контракта.
- Возвращать markdown, комментарии вокруг JSON или незаявленные поля.

## Политика пропусков

Пустое поле лучше честного `null` и warning, чем правдоподобный текст. Если неоднозначность нельзя разрешить из входных данных, оставить конфликт и передать его пользователю/следующему шагу на уточнение.

## Идемпотентность

Одинаковый transcript, версия схемы и версия промпта должны давать эквивалентный результат. Пересборка новой версией должна создавать новую версию профиля, а не уничтожать старую.
