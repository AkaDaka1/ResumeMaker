# ResumeMaker — общие правила проекта

## Назначение

Telegram-бот проводит интервью кандидата, сохраняет исходные данные в PostgreSQL и выпускает два PDF:

- **Human PDF** — визуально аккуратный документ для HR;
- **ATS PDF** — простой линейный текстовый документ для ATS.

Основной pipeline:

```text
Telegram -> interview -> raw transcript/facts -> normalizer -> typed JSON -> deterministic renderer -> 2 PDF
```

## Архитектурные правила

1. **Источник истины — исходные данные кандидата.** Нормализованный профиль и PDF являются производными и должны пересобираться.
2. **JSON — контракт, а не произвольный ответ LLM.** Профиль обязан иметь версию схемы, строгую валидацию, `null`/warnings для пропусков и evidence/source для существенных фактов.
3. **Никаких догадок.** Нельзя придумывать даты, должности, компании, метрики, навыки или контакты. Конфликты и неизвестные значения сохраняются явно.
4. **Агенты не работают с инфраструктурой напрямую.** SQL, файлы и очереди доступны только через узкие application tools.
5. **Рендеринг — обычный детерминированный код, не LLM.** Он принимает только валидный JSON и не изменяет смысл данных.
6. **Состояния и повторы явны.** Интервью и генерация документов имеют конечные статусы; Telegram updates и jobs должны быть idempotent.
7. **Версионируются схема, промпты, модели, шаблоны и renderer.** Старые профили не перезаписываются без миграции/новой версии.
8. **Язык интервью и язык резюме — отдельные настройки.** По умолчанию допускаются русский и английский; перед генерацией язык результата нужно подтвердить.
9. **Оплата и preview — отдельный release-gate.** До оплаты выдаётся только явно обозначенный watermarked preview; оригинальный итоговый файл выдаётся после успешной оплаты.

## Границы компонентов

- **Telegram/application:** команды, прогресс, пауза, повтор, удаление; без логики LLM/PDF.
- **Bot script:** базовые команды, согласия, баланс, статусы и платежи работают детерминированно и не расходуют LLM-токены.
- Правила Bot Script: [`agents/bot-script/AGENTS.md`](agents/bot-script/AGENTS.md).
- **Interview Agent:** диалог и сбор подтверждённых фактов; правила — [`agents/interviewer/AGENTS.md`](agents/interviewer/AGENTS.md).
- **Normalizer Agent:** transcript/facts → типизированный профиль; правила — [`agents/normalizer/AGENTS.md`](agents/normalizer/AGENTS.md).
- **Resume Renderer:** профиль → Human PDF и ATS PDF; правила — [`agents/resume-renderer/AGENTS.md`](agents/resume-renderer/AGENTS.md).
- **PDF Designer:** шаблоны и layout-specification; правила — [`agents/pdf-designer/AGENTS.md`](agents/pdf-designer/AGENTS.md).

«Агент» означает изолированный компонент с контрактом, а не обязательно отдельный сервис или deployment. Для MVP предпочтительнее одно приложение и worker, чем набор микросервисов.

## Сквозные требования

- До интервью: сообщить цель, собираемые данные и получить согласие.
- Пользователь может пропустить вопрос, исправить ответ, поставить интервью на паузу, удалить и экспортировать данные.
- Сырые сообщения не перезаписываются; полные PII не попадают в обычные логи и репозиторий.
- Секреты хранятся в environment/secret manager; PostgreSQL имеет миграции и ограниченный доступ.
- Внешние вызовы имеют timeout, ограниченные retry и безопасную обработку ошибок.
- LLM-агент запускается только после успешного списания баланса для конкретной операции; списание и создание job должны быть атомарными и idempotent.
- Бесплатные базовые сообщения не передают пользовательский текст во внешний LLM.
- Реальные пользовательские данные не используются в fixtures, golden-тестах и скриншотах.
- Любое изменение схемы профиля или PDF сопровождается fixture, валидацией и тестом.
- Согласие на обработку данных и согласие на передачу данных внешнему LLM API фиксируются отдельно: текст/версия, timestamp, пользователь и результат.
- Срок хранения MVP — 7 дней, но удаление должно учитывать raw transcript, derived JSON, payment data, audit log и итоговые файлы отдельно.

## Минимум тестирования

- состояния, идемпотентность и повторная доставка Telegram;
- валидные, неполные и противоречивые профили;
- кириллица, длинные строки, пропуски и многостраничные документы;
- извлечение текста и порядок чтения ATS PDF;
- интеграционный pipeline с подменённым LLM;
- негативные тесты на hallucination и prompt injection.

## Зафиксировано для MVP

- Язык: русский или английский, с определением по контексту и явным подтверждением результата.
- Провайдер: AnyModel; стартовая модель — DeepSeek v4 Flash, если доступна через нужный API-контракт.
- Сценарии первого релиза: backend developer и frontend developer; generic fallback обязателен.
- Импорт CV/LinkedIn не входит в первый релиз.
- Пользователь может запросить универсальное резюме или вариант под вакансию.
- Сценарии вакансий хранятся как версионируемые конфигурации; агент выбирает подходящий сценарий, но не меняет его обязательные поля.
- В первом релизе доступны два PDF-шаблона; выбор дизайна — будущая функция.
- В MVP файлы выдаются в Telegram; веб-ссылка не нужна до появления соответствующего требования.
- ATS preview до оплаты не выдаётся.
- Preview является платной операцией, но стартовый баланс пользователя должен покрывать одну preview-генерацию.
- В базе сохраняются текстовые данные и версии; бинарные PDF хранятся только в рамках retention-политики для итогового результата.

## До реализации нужно решить

1. Юрисдикция, текст согласия и политика удаления персональных данных.
2. Реальный API-контракт AnyModel: exact model IDs из `GET /v1/models`, цены/коэффициенты, лимиты, data retention и fallback. Chat API совместим с OpenAI; structured output/JSON Schema нужно подтвердить capability-тестом, так как в доступной документации это не гарантировано.
3. Правила preview: видимый watermark, разрешение, срок действия и защита от обхода.
4. Платёжный провайдер, валюта, webhook/idempotency и что делать при возврате платежа. В MVP поддерживаются два маршрута: Telegram Stars и СБП через выбранный российский банк/эквайера. Для каждого нужны актуальная проверка правил, тестовая интеграция и отдельная обработка возвратов.
5. Кто утверждает исправления после preview: повторный вопрос агента или ручная модерация.
6. Обязательные поля и критерии достаточности для каждого сценария вакансии.
7. Технический тип PDF-шаблонов: fillable fields, background PDF или только визуальный пример.
